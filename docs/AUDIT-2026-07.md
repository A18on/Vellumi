### A1. 图片保存路径硬编码 `assets/`，非默认文件夹时每次粘贴都产生死链
`Shared/Document/MoltenDocument.swift:304` vs `:309`
（合并两条同源发现）

- **为什么重要**：偏好设置 ▸ 文件 ▸ 图片文件夹名是一个已发货的可编辑输入框（`Mac/App/MoltenPreferencesWindow.swift:49,151`）。改成 `images` 后，PNG 写入 `images/`，Markdown 却记 `![](assets/pic.png)`，编辑器、HTML 导出、图片卡导出里全是破图，且永久写进磁盘文件。
- **修法**：`return "\(Self.imageFolderName)/\(target.lastPathComponent)"`，并对文件夹名做 percent-encoding（与 `Editor/src/main.js` 的 `rewriteAssetURL` 的 `encodeURI` 对齐）。补一条把 `Vellumi.imageFolderName` 设为非默认值的测试——`Tests/MoltenImageAttachmentTests.swift:36,46,55` 只测了默认值，所以套件是绿的。

### A2. `reloadIfCleanAndChangedOnDisk` 缺 `sourceModeActive` 守卫，源码模式打字被外部写入抹掉
`Shared/Document/MoltenDocument.swift:346-360`
（合并"外部变更摧毁源码模式输入"与"未守卫的 change 消息"两条——校验证实后者的真实触发点就是这里）

- **为什么重要**：用户在源码模式改文件时，任何外部写入（git checkout / iCloud / Dropbox）触发 `presentedItemDidChange`（`:339`），代码无条件从已停摆的 web view 拉取旧内容并喂给 `editorTextDidChange`（`:255-260`），`document.text` 被覆盖为进入源码模式那一刻的旧文本，而 NSTextView 仍显示新输入；⌘W 关闭时源码编辑消失。
- **修法**：抄 `refreshTextFromEditor:205` 的同一守卫——`guard !sourceModeActive, let editor = editorViewController else { performReloadIfCleanAndChangedOnDisk(); return }`。更好的做法是把"哪个界面是权威"这个判断抽成一个新鲜度原语，两处共用。也可以直接在 `editorTextDidChange:255` 首行加 `guard !sourceModeActive else { return }`，一并关掉所有入口。
- **工时**：15 分钟

### A3. `release.sh` 从不构建编辑器 bundle，干净 clone 出来的发布包是一个空白编辑器
`scripts/release.sh:28-40`

- **为什么重要**：脚本从 `xcodegen generate` 直接跳到 `xcodebuild build`，全仓库对 `scripts/build-editor.sh` 的唯一引用在 `README.md:16`。`project.yml` 把 `Resources/dist` 声明为 folder reference，空目录静默拷贝、构建返回 0；`.gitignore` 只保留 `.gitkeep`，`Editor/build.mjs:13` 又会先 `rmSync` 整个 dist。结果：一次失败/中断的 npm build 或一次干净 clone，就能产出一个每个文档都是白屏的 DMG，管线里没有任何东西会失败。
- **修法**：release.sh 第一步加 `"$ROOT_DIR/scripts/build-editor.sh"`，打包前硬断言 `test -s Resources/dist/editor.js && test -s Resources/dist/index.html`，并在签名后校验 `$APP/Contents/Resources/dist` 里同样存在这两个文件。
- **工时**：10 分钟

### A4. Sparkle appcast 工具在错误的 DerivedData 里找，静默跳过 appcast 更新
`scripts/release.sh:99`

- **为什么重要**：`:20/:38` 用私有 `DERIVED="$ROOT_DIR/.build/release"`，而 `:99` 只在 `$HOME/Library/Developer/Xcode/DerivedData` 里 `find ... | head -1`。干净机器上会取不到，走到 `:110` 只打一行 WARNING 然后 exit 0——你会带着 DMG 打 tag、发布，而所有已安装用户的 Sparkle 永远收不到这个版本。`head -1` 命中别的工程时还可能用错版本的 `generate_appcast`。

### A5. 导出丢失所有已渲染的代码块
`Editor/src/main.js:712-715`

- **为什么重要**：收尾清扫 `clone.querySelectorAll(".label-wrapper, .milkdown-icon, [data-v-app]")` 对不含 li/img/table/pre/blockquote 的元素一律 `remove()`。Crepe 的 CodeMirror nodeView 把 Vue app 挂在代码块自己的容器上（`@milkdown/components/src/code-block/view/node-view.ts:79-80,130-138`，Vue 在容器上打 `data-v-app`），初始化后占位 `<pre>` 被删除、CodeMirror 只产出 `div.cm-*`，于是每个**滚动到过视野的**代码块都被整块删掉。同一文档因为用户滚动位置不同，导出结果不同。经真实 WKWebView 复现确认。
- **影响面**：`Mac/Export/MoltenExporter.swift:12`（HTML 导出）与 `Mac/Editor/MoltenWorkspaceViewController.swift:74`（图片卡导出）。PDF/打印走活 web view，不受影响。
- **修法**：清扫前先显式处理代码块：对每个 `.milkdown-code-block`，用 ProseMirror 节点文本（或 `.cm-content` 的 textContent 按行拼接）构造 `<pre><code class="language-X">` 并 `replaceWith`；然后把最终清扫的选择器从通配的 `[data-v-app]` 收窄为 `.label-wrapper, .milkdown-icon` 加已知空壳白名单。
- **工时**：半天

### A6. 表格里只要有一张图，导出时整张表被这张图替换
`Editor/src/main.js:701-710`

- **为什么重要**：图片折叠循环遍历所有 `[data-v-app]`，只要找到任意后代 `<img>` 就把**整个元素**换成裸 `<img>`。Crepe 的表格 nodeView 同样把 Vue app 挂在 `.milkdown-table-block` 外层 div 上，`querySelector("img")` 会穿进任意单元格。已实测：含图表格导出后既无 `<table>` 也无其他单元格文字。且该循环跑在 `:713` 的 pre/table 保护之前，保护根本没机会生效。
- **修法**：把折叠范围收窄到真正的图片 nodeView（`.milkdown-image-block, .milkdown-image-inline`，或要求 `:scope > img`），并跳过任何同时包含 `table` / `li` / `.cm-editor` 的 `[data-v-app]`。
- **工时**：1 小时（与 A5 同一函数，建议一起改）

### A7. 只打开不修改、按 ⌘W 关闭，文件被静默重写
`Shared/Document/MoltenDocument.swift:201-221`

- **为什么重要**：`canClose:192` 走 `refreshTextFromEditor`，只要拉回的序列化结果与 `text` 不同就 `updateChangeCount(.changeDone)`（`:217`）。Crepe 在加载时会规范化 Markdown，所以**任何非 Crepe 规范形式的文件**（`* item` 列表、setext 标题、4 空格缩进代码块、引用式链接）必然不同。`autosavesInPlace = true`（`:30`）下 `super.canClose` 会就地自动保存后关闭——用户没保存过、也没被询问，磁盘文件已被改写。同一根因还导致：干净但非规范的文档在任何外部写入后被标脏，`performReloadIfCleanAndChangedOnDisk:363` 于是在 `guard !isDocumentEdited` 处放弃，随后把 checkout 前的旧内容自动保存覆盖掉外部变更。
- **修法**：引入 `normalizedBaseline`——让 `normalized` 桥消息带上序列化后的文本（`Editor/src/main.js:473-476` 已经算出该值），或记录首次 pull 的结果；`refreshTextFromEditor` 仍然采纳 `markdown` 到 `text`，但只有 `markdown != normalizedBaseline` 时才 `.changeDone`。`canClose` 单独走一个"只刷新不标脏"的变体。
- **工时**：2-3 小时（改动落在死锁修复过的同一段代码，需谨慎，务必保持"进入保存机器之前完成 pull"的顺序不变）

### A8. 仅改 front matter 的编辑永远不标脏，改动被丢弃
`Shared/Document/MoltenDocument.swift:236-240` + `:256`

- **为什么重要**：`adoptSourceText` 把脏标记完全委托给 `editorTextDidChange`，而后者首行是 `guard markdown != text else { return }`。`MoltenFrontMatter.split`（`Shared/Document/MoltenFrontMatter.swift:15-37`）在只改 YAML 值时正文逐字节相同，于是 `updateChangeCount` 一次都不调用：⌘S 不写盘、⌘W 不自动保存，YAML 编辑静默消失。`Tests/MoltenQuickOpenAndSourceTests.swift:36,48` 两个用例都同时改了正文和 front matter，所以完全没覆盖。
  次要路径：`setFrontMatter:244` 正确标脏后，在编辑器里打一个字再 ⌘Z，`:258` 会因 `markdown == savedText` 走 `.changeCleared`——而 `savedText` 只记正文（`:26,95,150,387`），文档被清干净而 front matter 仍与磁盘不同。
- **修法**：加 `private var savedFrontMatter: String = ""`，在 `read(from:):95`、`save(to:)` 成功分支 `:150`、`performReloadIfCleanAndChangedOnDisk:387` 三处与 `savedText` 一起快照；把 `:258` 的判断改成 `(markdown == savedText && frontMatter == savedFrontMatter) ? .changeCleared : .changeDone`；`adoptSourceText` 先比对并赋值 front matter，变化时无条件 `.changeDone`。
- **工时**：1-2 小时

### A10. 源码视图内容永不重新同步，Revert / 外部重载被撤销

## B. 值得做 — 明确的用户可见收益

### B1. 查找 / 计数 / 替换用了三套大小写策略，替换按钮静默失效
`Editor/src/main.js:627`（`window.find(term, false, ...)` 不区分大小写）、`:639-643`（计数不区分）、`:738`（replaceAll 区分）、`:764`（replaceNext 要求全等）

- 文档里三个 `Hello`，搜 `hello`：标签显示"3 处匹配"、⌘G 能逐个跳，但"替换"每次都只是移动选区什么也不改，"全部替换"返回 0。已实测（countMatches=3 / replaceNext=false / replaceAll=0）。
- **修法**：统一为不区分大小写——replaceAll 用 `text.toLowerCase().indexOf(term.toLowerCase(), index)` 收集区间（加长度校验），replaceNext 比较两侧 `.toLowerCase()`。或在查找栏加显式 Aa 开关并把 `caseSensitive` 贯穿四个桥方法。
- **工时**：1-2 小时

### B2. 图片卡预览每敲一个水印字符就从零重排版
`Resources/imagecard/card.html:930-936, 579, 1261, 1272` + `Mac/Export/MoltenImageCardExportView.swift:73,239-241,335-370`

- 水印 TextField 直接绑定，每次按键触发 `optionsDidChange → applyOptions → setOptions → render()`，无防抖、无取消；`render()` 只在 `paginateRenderedHtml` 返回后才检查 `state.renderGeneration`，并发的分页任务争抢同一个 `measureStage`。分页本身还很贵：`renderNodesToMeasure` 每测一次都深克隆整页节点并对全部内容重跑 `hljs.highlightElement` + `katex.render`（`:798-824`），且每 6 次测量 `await` 一次裸 rAF（`:579,1261,1272`）。
- **修法**：优先给选项变更加 200ms 防抖 + 代数取消（这一条就能治好普通文档的卡顿）；其次测量时跳过 `applyRuntimeRendering`，只在 `capturePageDataURL` 里做高亮/公式；把固定次数的 yield 换成时间预算（`performance.now() - lastYield > 8`）；按 bodyHTML+尺寸缓存分页结果，主题/水印变更复用。
- **工时**：防抖 1 小时；完整优化 1-2 天

### B3. 图片卡导出：一次性单条桥消息 + 主线程解码/打包 + 渲染进程死了永不返回
`Mac/Export/MoltenImageCardExportView.swift:406-425, 427-449, 236` + `Resources/imagecard/card.html:1455-1470`
（合并三条同源发现）

- `captureAll` 把每一页的 base64 data URL 累积进一个数组后一次性 post，Swift 侧在 `@MainActor`（`:175`）上同步解码全部页（`MoltenImageCardTypes.swift:158-174` 每页还多一次 `String(payload)` 拷贝），再同步 CRC32+拼接整个 zip（`:218-241`）。同一时刻活着 4 份完整图集，全流程无页数上限。模型是 `WKNavigationDelegate` 却没实现 `webViewWebContentProcessDidTerminate`（对比 `Mac/Editor/MoltenEditorViewController.swift:443-446`），也没有超时；渲染进程被回收时完成回调永不触发，`isExporting` 永远为 true。`finish():236` 的 `pendingCaptures.removeAll()` 还会吞掉回调而不调用。
- **修法**（按性价比排序）：① 实现 `webViewWebContentProcessDidTerminate`，把 `pendingCaptures` 全部以失败结束；`finish()` 改为逐个用取消错误调用而非 `removeAll()`；加 120s 看门狗。② 改用已存在的 `capturePage(index:requestID:)`（`card.html:1443`）逐页拉取、逐页落盘/追加 zip 并及时释放。③ 加页数上限与超限告警。
- **工时**：① 1 小时；② 1 天

### B4. 重签名丢掉 hardened runtime，并把 `get-task-allow` 带进发布包
`scripts/release.sh:60`

- `codesign --force --sign - --preserve-metadata=entitlements "$APP"` 带显式列表时只保留 entitlements，不保留 `runtime` 标志。已在构建产物上实测：`flags=0x2(adhoc)`（应为 `0x10002(adhoc,runtime)`），且 `codesign -d --entitlements -` 返回 `com.apple.security.get-task-allow=true`——`Vellumi.entitlements` 从未声明它，是 Xcode 注入后被 preserve 带过来的。一个持有用户文件夹 security-scoped bookmark 的沙盒编辑器不应允许同用户下任意进程附加调试器。这也让 `release.sh:12-13` 那句"公证无需其他改动"的注释是错的。
- **修法**：`project.yml` Release 配置加 `CODE_SIGN_INJECT_BASE_ENTITLEMENTS: NO`；`:60` 改为 `codesign --force --sign - --options runtime --entitlements "$ROOT_DIR/Vellumi.entitlements" "$APP"`；在 `:62-67` 的 belt-and-braces 块里加两条断言（有 runtime 标志、无 get-task-allow），不满足 exit 1。
- **工时**：30 分钟

### B6. 字数统计每次刷新算三项、用一项，且用了最慢的写法
`Mac/Editor/MoltenWorkspaceViewController.swift:215-219`

- 字符统计在 per-scalar 闭包里重建 `CharacterSet.whitespacesAndNewlines` 并物化整个 scalar 数组；段落统计再把全文物化成子串数组。实测（swiftc -O，976 KB 混合中英文）：字符行 37-49 ms、段落行 17-18 ms，而 `MoltenWordCount.count` 只要 1.6 ms；把 CharacterSet 提出闭包并改 for-where 后降到 ~5 ms。`renderStatusLine:160-183` 每次只用其中一项。
- **修法**：把 CharacterSet 提出闭包（或像 `MoltenWordCount` 那样直接比较标量值）、用 for-where 代替 `.filter{}.count`、用扫 `text.utf8` 数 `\n\n` 代替 `components(separatedBy:)`、只算当前显示模式需要的那一项，最好三项合进一次遍历。
- **工时**：1-2 小时
- **注**：这段跑在 `statsQueue`（`:45`，qos .utility）上，不阻塞主线程——收益是后台 CPU 与电量，不是打字流畅度。

### B7. `focusEditingSurface()` 在源码模式下把焦点抢到隐藏的 web view

### B8. 首启欢迎文档只有中文
`Resources/Welcome.md:1`、`Mac/App/MoltenAppDelegate.swift:44`、`project.yml:46-47`

### B9. 搜索界面在加载中显示"无匹配"；Quick Open 不重置上次查询
`Mac/Projects/MoltenProjectsWindow.swift:295-296, 414-417`、`Mac/Projects/MoltenQuickOpenWindow.swift:35-40, 116-120`
（合并两条）

- `runContentSearch` 先置空 `contentResults` 再派发异步全文遍历，下一帧就渲染"无匹配"，大项目下这个假结果会停留数秒，没有任何进度提示。`show()` 只调 `model.reload()`，`query` 挂在单例 model 上从不重置，第二次 ⇧⌘P 打开时仍是上次的搜索词和结果。

- **工时**：1 小时
- **注**：查询保留本身是可辩护的（Xcode Open Quickly 同样如此），如果你觉得它有用可以只修 loading 状态。

### B10. 失败只用一声系统提示音表达
`Mac/Projects/MoltenProjectsWindow.swift:223`（重命名同名冲突）、`:143`/`:211`（bookmark 解析失败）、`:159`（新建笔记）、`Mac/Editor/MoltenWorkspaceViewController.swift:76` 与 `Mac/Export/MoltenExporter.swift:14`（导出取不到 HTML）

## 明确不要做

1. **不要给 autosave 加异步预拉取钩子**（`MoltenDocument.swift:136-155`）。这正是已修复的关闭死锁的形状——在 NSDocument 保存机器内部做主队列异步跳转。要么改注释、要么在 JS 侧封顶防抖，不要动 Swift 侧的保存路径。

2. **不要把 `performReloadIfCleanAndChangedOnDisk` 的协调读改成异步**（`:372-376`）。校验方已驳回"这和已修死锁同类"的论证：`filePresenter: self` 已豁免本文档，读 claim 不需要本进程主线程回调，不存在自死锁；NSDocument 自己在 open/save 全程也是主线程同步协调文件访问。这条路径还被"干净 + mtime 更新 + ≤20 MB"三重门禁，Markdown 通常只有几 KB。改成异步反而要重新校验 `isDocumentEdited` 和 mtime，引入新的竞态。

3. **不要改窗口 frame autosave name**（`MoltenDocument.swift:70-75`）。上面三行 `tabbingMode = .preferred` / `tabbingIdentifier`（`:49-50`）的注释明确说明这是刻意选择——文档默认合并成标签页而非独立窗口，所以"两窗完全重叠不级联"的场景需要用户先手动拆分标签页；共享 frame 也是 `:66-69` 注释里写明的设计意图。

4. **不要优化 Quick Open 模糊匹配**（`Shared/Projects/MoltenFuzzyMatch.swift:10-11`）。原报告的"跨所有项目文件夹的每个 md 文件"前提是错的：`MoltenProjectStore.markdownFiles` 用了 `.skipsSubdirectoryDescendants`（`:105-108`），只枚举每个文件夹**顶层**。实测 500 候选 0.7 ms、5000 候选 7.2 ms，任何现实语料下都不可感知。

5. **不要为每个 Milkdown 组件补 nodeView 挂载测试**。v0.4.0 那个 bug 的机制是 `editorViewOptionsCtx` 会**整体替换** milkdown 从 components 收集的 nodeViews 映射（`Editor/src/main.js:442-448`），代码块、图片块、列表项、表格是同生共死的——现有的代码块哨兵测试（`Tests/MoltenEditorBridgeTests.swift:332-346`）已经能抓到完全相同的回归。额外的选择器还是未经验证的猜测。

6. **不要为 `CURRENT_PROJECT_VERSION` 加断言而排期**（`project.yml:63-64`、`scripts/release.sh:25`）。风险真实（Sparkle 比较的是 CFBundleVersion，忘记 bump 会让所有用户"已是最新"），但两个字面量是相邻两行、历来一起改。如果做，就顺手塞进 A3/A4 的 release.sh 改动里：构建后用 PlistBuddy 读 `CFBundleVersion`，断言严格大于 `appcast.xml` 里现有最大的 `<sparkle:version>`，不满足 exit 1。5 分钟的事，不值得单独立项。

7. **不要单独优化图片卡的主线程 zip/CRC**。做 B3 的流式方案时它自然消失；单独改收益 < 1 秒且发生在模态面板上。

## 需要你先测量或先决策的

1. **JS bundle 拆分（C 表最后一项，1-2 天）**——需要数据才能决定。测法：开 1 个文档，再开 5 个，`ps -axo rss,comm | grep -i 'Web Content'`，看每多一个文档的 RSS 增量。目前已确证的只有磁盘体积（6.39 MB）和包内构成（mermaid 子树 49%）；`docs/PERF.md` 显示 28.5 KB 文档开启总耗时 170 ms，esbuild 又把 mermaid 的图表 import 包进了惰性 `__esm` 初始化器，所以 elkjs/cytoscape 是"解析并驻留但未执行"。如果每文档 RSS 增量低于 ~80 MB，这条不值得做。

2. **图片卡流式导出（B3②，1 天）**——需要你定：是接受"超过 N 页给出警告并拒绝"这个产品行为，还是坚持无上限但改成逐页流式。前者半小时、后者一天。

3. **编码保持策略（C 表 UTF-16 项）**——需要你定要不要在 `MoltenDocument` 里引入编码状态。我的建议是只做那个 15 分钟的子集：UTF-8 分支遇到 NUL 字节就拒绝（那是真损坏），BOM 保持不做——转成无 BOM UTF-8 字符无损，且任何工具都读得了。

4. **无障碍与本地化的投入范围（C 表 a11y 项，1-2 天）**——这是一整包 polish，没有单点故障。如果你打算把 Vellumi 推给中文以外的用户，B8（Welcome.md）+ `<html lang>` 一行 + 查找栏两个按钮的标签是最小可行子集（半天）；完整的 a11y 审计建议等有真实用户反馈再说。
